# Supabase — guardrails

> **Before any SQL migration, RPC, grant, pgTAP test or edge function, load the `supabase-rpc`
> skill** (RPC template, `_v2` compatibility, grants, Vault, Storage). Pitfalls: this layer's
> `gotchas/` files (`.claude/agentic-kit/layers/supabase/gotchas/`).

- **Everything targets the local database** (Docker). The cloud is reached only through CI: a push
  to a branch that deploys **is** a deployment. Remote or destructive commands (`db push`,
  `db reset`, `functions deploy`, `link`, `--linked`, `--db-url`, `--project-ref`) need the user's
  approval.
- Never edit a migration that has been pushed: write a new one. The project's data-model doc, if it
  keeps one, changes in the same commit as the migration; types are regenerated by the project's
  pinned-CLI script (`npm run gen:types`), never by hand.
- **An RPC or edge function in production never changes its contract in place** (store builds call
  it for their whole life): otherwise a `_v2`. When in doubt, `_v2`.
- Every RPC: `SECURITY DEFINER`, `SET search_path = ''`, identity from `auth.uid()`, `REVOKE` +
  `GRANT … TO authenticated`; RLS enabled with no policy on every table; pgTAP test first.
- No secret in a migration (Vault); Storage files are deleted through the Storage API, never in SQL.
