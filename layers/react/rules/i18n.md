# React — internationalization

- `react-i18next`. **No hardcoded text**: every displayed text goes through `t('…')`
  (`useTranslation()`, `i18n.t` outside React). No local `Record<string, string>` in place of a
  real key. Exception: dev tools, written in plain text so they leave the production bundle with
  their code.
- **Never `t(key, { defaultValue: … })`**: a missing key must show (it falls back to the raw key);
  add it to the translation files.
- **English is the reference language and the default one**: a key is written in English first,
  the other languages translate it in the same commit; every file keeps exactly the same keys.
  English is the fallback locale. Wherever the user's language is unknown, use English: native
  strings (iOS development region `en`, permission texts), server-side pushes and emails.
- **Keys**: kebab-case, **flat** dot hierarchy. The scope name repeats the owning file's name in
  kebab-case, without its role suffix:
  - `core.*` — shared (several components, or a mapper / an enum table);
  - `component.<component>.*`, `container.<container>.*`, `page.<page>.*`;
  - `action.<action>.*` — feedback (toast, alert) triggered by a mutation rather than rendered by
    a component.

  A string used in two places moves to `core.*`. Existing keys of a project that followed another
  structure are not renamed; new keys follow this one.

- Plurals: `t('key', { count })` with `key_one` / `key_other`, never "item(s)".
- A truly dynamic key: type `` Extract<ParseKeys, `prefix.${string}`> ``, never `string`.
- A key that loses its last use leaves every translation file in the same pass (the project's
  script sees neither `<Trans i18nKey>` nor keys stored in an array: check with `grep`).
- Dates, numbers, prices: formatted client-side with the current language (`Intl`, `date-fns` +
  locale), never `toFixed` + a symbol, never a hardcoded currency. **No human-readable label
  stored in the database**: technical keys, translated client-side.
